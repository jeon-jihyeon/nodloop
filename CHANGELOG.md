# Changelog

Every release tag publishes the plugin, the darwin and linux binaries of `nodloop` and, from 0.7.0, `nodloop-server`, and both SDKs under one version. Versions before 0.6.0 reviewed incident data, which left this repository in 0.6.0.

## Unreleased

### Breaking
- Automatically inferred knowledge scopes leave out the reserved `correlation` label as they already leave out `host`. An external conversation or request can keep this label on its runs without tying a lesson to that request. Existing stored scopes stay unchanged. If an integration already used `correlation` as a scope key, pass a nonempty explicit scope to keep that boundary when proposing new knowledge
- A write counts as your decision only when the call proves a person: `nodloop` at a terminal of your own outside an agent session, or an approver key of nodloop-server added with `--person`. Any other approve, retire, reaffirm or compaction approval is recorded as an agent proposal, an `intervention` trace with `authority` agent and `proof` none, and the knowledge stays as it was, since a model in a session approved four lessons nobody approved in two of seven headless chains
- Every setting that changes what is recorded, kept or sent, or who judges for you, saves only at a terminal of your own outside an agent session, like `config approver`: `config session_mode <mode>`, `config holdout <share>`, `config retention <days>`, `otel set`, `otel unset`, `llm set`, `llm unset`, and `classifier set` and `unset` of every point, the critic included. From a script or the shell of an agent they fail and change nothing, since who predicts your decisions, which model judges for you, whether your reactions are recorded, which sessions get no lesson, what is kept and where your records and with `--content` every output and lesson are sent are yours to decide. Printing each of them works from anywhere
- `NODLOOP_SESSION` no longer sets the session mode. Set it with `config session_mode <mode>` at a terminal of your own, since the env of a project `.claude/settings.json` reaches the hooks and an agent that edits that file would switch recording off for you
- `NODLOOP_LLM_MODEL` no longer reaches a pass that runs in the background, such as the capture, `knowledge curate --daily` and `knowledge consolidate --daily` a hook starts, so the reaction point that reads your words, the drafter and the critic run the model of config.json there. Set it with `llm set claude --model <m>` at a terminal of your own. A command you run still takes the variable, and `NODLOOP_CLAUDE_BIN` and `NODLOOP_RECORD_DIR` still reach every process
- Go package: `Approve`, `ApproveIn` and `Retire` record an agent proposal and return it as an `Intervention` with `Authority`, `Proof` and the version it names, and the ledger stays as it is. A Go service that serves a person sends the approval to nodloop-server under the person's key. `Judge` and `Outcome` without `Reviewer` fail with `ErrReviewerRequired`, an empty approver fails with `ErrApproverRequired` and `nodloop` as an approver fails with `ErrApproverReserved`
- Python and TypeScript SDKs: `approve` records a proposal unless the client holds a key of nodloop-server added with `--person`, and answers the status unchanged with `proposal` naming the intervention. `judge` requires the reviewer and takes everything after the verdict by name: `judge(run, verdict, reviewer="ann", reason=...)` in Python, where a reason passed third now raises `TypeError` instead of being recorded as the reviewer, and `judge(run, verdict, { reviewer: "ann", reason })` in TypeScript, where options without a reviewer fail. `outcome` over stdio without a reviewer fails
- MCP: the plugin starts `nodloop mcp --agent`, which lists no `approve`, `reaffirm` or `approve_compaction` and records every verdict and outcome with reviewer `session` whatever the call names. Over stdio `approve`, `reaffirm` and `approve_compaction` always record a proposal, each answering `proposal`. `feedback` and `outcome` over stdio without a reviewer fail
- nodloop-server: only a key of role approver added with `key add --person` decides, under its name, and a verdict or an outcome under such a key that names anyone but `session` is recorded under the key name too, so no call records a proven verdict under another name. Every key saved before records proposals until you remove it and add it again with `--person`. `key add --person` runs only at an interactive terminal of your own outside an agent session, like the commands of `nodloop` that decide, so a script or an agent's shell can add a key of a service and never one that proves you. `key list` adds a column naming who holds each key, and a key named `nodloop` is refused when added and when `serve` starts
- nodloop-server with PostgreSQL: every append takes a lock of its tenant and record kind, so a records page reads the rows in the order they committed. During a rolling deploy a 0.9.0 replica appends without that lock, so a page a 0.10.0 replica serves may miss its rows until every replica runs 0.10.0. Run every replica on 0.10.0 before clients read pages
- CLI: `knowledge approve`, `retire`, `reaffirm`, `approve-compaction`, `knowledge import` and `config approver <name>` decide only at an interactive terminal outside an agent session, which the variable Claude Code, Codex, Cursor or Copilot CLI sets for the commands its agent runs marks. From a script or a Bash call of Claude Code the first four print a `proposal` line and change nothing, and the last two fail. `--approver` falls back to `approver` of config.json and then to `person`. `feedback add` and `feedback outcome` without `--reviewer` fail. `knowledge ask` is gone, and `immediate` reads as `deferred` from config.json while `config session_mode immediate` is refused
- Session: the start hook no longer walks you through every waiting draft. curate sorts the drafts and the stop asks at most one question per session about what it prepared, so a draft waits for that question, `/nodloop:nod` or `knowledge waiting`
- The name `nodloop` is reserved for what nodloop carries out: no approve, retire, reaffirm or compaction approval takes it from any caller
- Every record nodloop appends carries `schema_version`, the version of its published schema, as its last field: runs and every other trace, verdicts, outcomes, knowledge records and the guard log. A record of an earlier release without it reads as version 1, so a reader that compares stored lines byte for byte sees the new field on new lines only
- A classify trace of the reaction point keeps your message and the answer it judged only as an HMAC under `hmac.key` of the record directory, and its questions by name, so no trace holds your words. The member that defers to the conversation is recorded as `conversation` instead of `claude`
- The reviewer `nodloop` is reserved for the capture of a session, which reads your own words from the transcript: MCP `feedback` and `outcome` over stdio and under any nodloop-server key, `feedback add` and `feedback outcome`, the Go `Judge` and `Outcome` and `judge` and `outcome` in both SDKs refuse it with `ErrReviewerReserved` and record nothing, since a verdict forged under it could settle or raise a dispute between the conversation and the capture. The agent server still records `session` whatever the call names
- `report loop` counts a verdict as `judged` only when its call proved the person: `feedback add` at a terminal of your own outside an agent session, or MCP `feedback` under an approver key of nodloop-server added with `--person`. A verdict that only names someone, from `feedback add` in a script, the Go `Judge`, MCP `feedback` over stdio or under any other key, counts as `named`, and so does every named verdict recorded before this release. The totals add `named` between `judged` and `inferred`, and each item adds `named followed n of m` and `named repeat n` before the inferred columns, in the text and as `named`, `named_judged`, `named_followed` and `named_repeat` in JSON
- `report effect` keeps every verdict in `judged` and adds `named` and `inferred`, the judged runs no proof backs, right after the producer column in the text, so the columns from `units` on move two to the right
- Verdicts of reviewer `nodloop`, which the capture records from your own words, count as inferred like those of `session`, with their reason redacted. When the conversation and the capture both judged a run and disagree on whether it corrects, the run counts as disputed: no report counts its inferred verdict and no extraction drafts a lesson from it. A withdraw takes back what both inferred before it, and an extraction reads a person's verdict over a later inferred one. A reader of the records that counts every reviewer but `session` as a person must count `nodloop` as inferred too
- `records prune --dry-run` prints `would roll up <r> closed cycles and prune <n> runs, <m> classify traces and <t> turn, instructions and capture traces older than <cutoff>, kept ...`, and the cutoff of both prune lines is where the prune stops: the start of the open cycle of curate when that comes before the cutoff of the retention
- `report effect` reads every cycle of curate whole from its start and a closed cycle that was rolled up from its rollup alone, so once a cycle exists its window line and `since` name the start of the first cycle when that comes before the retention window, and the counts of a cycle stay as they were after a prune removes its runs
- A conflict an extraction finds is drafted as the next version of the item or candidate it contradicts, with the scope and veto of that version and the corrected run alone as its evidence, since the old evidence teaches the opposite. `knowledge extract` prints a `candidate` line for it, `propose_extraction` answers its `candidate`, and the extract trace names it in `candidate` beside `related` with conclusion `conflict`. Before, a conflict proposed nothing
- In a mode that infers the stop hook starts `knowledge curate --daily` in a process of its own at most once a day, kept in `curate.json`. It retires as `nodloop` the waiting lessons your record already settles: one whose text, ignoring case and spacing, is that of an approved lesson its runs receive, with reason `duplicate`, one whose correction no longer stands, with `no_evidence`, and one scoped to a temporary directory or a `scratchpad` path, with `temp_scope`, and a lesson that repeats an older waiting one adds its runs to that one and is retired with `duplicate`. So `knowledge waiting` lists fewer lessons. The pass calls the model: it drafts each correction no extraction read, and the judge asks three claude calls about each waiting lesson that no rule sends to you, once per lesson. Nothing is approved for you while curate runs in shadow
- The stop hook no longer starts `knowledge extract`. In a mode that infers it starts `nodloop session capture` on the transcript Claude Code names, which reads your own words and drafts the lesson of each answer you corrected, your own verdicts included, so a correction counts whether or not the conversation called the feedback tool. A Codex stop, whose transcript is in no format the capture reads, starts the capture with no transcript, which drafts the answer the turn followed when the conversation corrected it and runs the curate pass, so that correction is decided at the next stop. Cursor and Copilot record no run, so nothing of theirs is captured
- `export otel` changed shape for tracing tools: protobuf is the default, a verdict or an outcome is its own evaluation span linked to its run instead of an event on a run span sent again, every verdict and outcome record goes once instead of the newest one, verdict reasons and outcome notes stay home without `--with-content`, `--endpoint` sends traces only, and the line reads `exported <r> runs, <v> verdicts, <o> outcomes, <c> model calls, <q> questions, <d> decisions and <j> judgments`. The span ids of runs stay the same
- Only the 9000 chars of a run are capped. The cap of ten items per run and the compaction offered at six items are gone, so an eleventh short item approves. The MCP folder answer drops `item_budget` and `compaction_due`, `over_budget` counts chars only, `knowledge approve` prints no compaction line, and `Approval` drops `compaction_due` in Python and `compactionDue` in TypeScript
- `report critic --json`, the MCP `report` answer and `GET /v1/reports/critic` hold `{critics, reactions, capture}` instead of an array of critic rows
- `report loop` tells what nodloop approved for you apart from what you approved: a drafts line adds `by nodloop n` right after `approved n`, which moves the columns after it one to the right, and `approved_nodloop` in JSON, and an item line ends with `approver <name>` and adds `approver` in JSON

### Added
- The stop hook asks you one question per session about what curate prepared, at the end of an answer and only once everything before it went through: a change your recorded decisions do not settle, one citing a run of your session before older ones, else a change curate carried out drawn for an audit, else one it would carry out once out of shadow, as well as the widening and the activation the knobs offer. Claude Code gets it through Stop `additionalContext` with no `decision`, so no error label shows, and is told to put its lines up to Prepared word for word into one AskUserQuestion call with header `nodloop <key>` and the two options with the descriptions nodloop names, since a model that worded the question itself left out your words on 10 of 10 Haiku runs. A click counts when the call holds every line of the question, the header and each option with its description, however the model spaced them or added lines, so a question or an option a model worded itself under the key records nothing. Your click there or the first word of your next message, both read by the capture from the transcript Claude Code keeps once that turn ends, records an `answer` with proof `reply` under `approver` of config.json or `person` and carries out your choice through the ledger, which names the answer in `decision`. The prompt hook only keeps that word from being judged and records nothing, since any process can pipe a prompt into it. Codex, Cursor and Copilot are shown no question and no notice, since no code reads your answer there, so the question waits for your next Claude Code session or `/nodloop:nod`. A question two other sessions showed with no answer is recorded `no_answer`, and a proposal an agent made at your request is asked at the stop of that turn in any mode but `off`. When curate approved or withdrew lessons that reach a place, Claude Code shows one line through Stop `systemMessage` instead, once per session. Each question and notice is an `expose` trace with its key, choices, round, run, the runes of its text, an HMAC of it and for a question an HMAC of each line a click must hold, and the probability it was asked with
- `nodloop session capture --session <id> [--transcript <path>] [--model <m>]` reads only the transcript Claude Code keeps for the session, `<session id>.jsonl` in a project folder under `projects` of `~/.claude` or `CLAUDE_CONFIG_DIR`, and refuses any other path, so no command an agent runs can hand it words of its own. An AskUserQuestion call of a question of the stop waits for its result before the capture reads past it, so a click counts only as the result of its call, and only when the question of that call is the text the stop showed, matched by the HMAC its `expose` keeps, so a model that asks a question of its own under the header records no answer. It reads the messages you typed since the last capture of the session, from the byte offset its `capture` trace keeps, and asks the reaction point in one call per message whether it corrects or approves the answer it followed and whether it asks to stop following each lesson that answer had in its context. A sure correction or approval is recorded with reviewer `nodloop` and your message redacted and cut at 500 runes as its reason, the words the judge of curate reads, and a sure request to stop following a lesson is a signal curate reads. Tool results such as an AskUserQuestion answer, slash commands, task notifications, interruptions, lines of subagents and the reminder, file and selection blocks the host or an IDE adds beside what you typed are never read as your words, a click on a question of the stop and a first word that answers it are read as your answer and never as a verdict, and the first capture of a session reads only the turn its stop ended. Every call is a classify trace of point `reaction` that keeps your message only as an HMAC, through the endpoint set for the point first and `ClaudeReaction`, one `claude -p` call of the llm default model, otherwise. Then it drafts the lesson of each run it judged whose verdict corrects it, a person's verdict winning, that no record cites, and runs one curate pass when a draft went through or a signal was read. Captures of one record directory take turns on `capture.lock`, so two stops in a row never read a message twice. In `manual` mode the stop starts the capture too, which then reads only your answers to the questions of the stop and judges nothing else, so a proposal you asked for in that mode is answered by your click as well
- curate withdraws a lesson nodloop approved when an extraction finds a correction that goes against it, with reason `conflict`, or when the capture read your words asking to drop it, with reason `words`, in shadow first like every withdrawal. Your words on a lesson you approved yourself become a question of rule `person_item` instead. Each signal is decided once
- `nodloop knowledge curate [--daily] [--model <m>]` sorts each waiting lesson by whether your recorded decisions settle it and prints one line per decision with its action, kind, version, tier and rule or judge outcome. What only you decide waits for one question to you: a lesson that replaces or was built on one you approved, one that reaches runs no lesson you approved reaches, one with a veto, one whose approval needs room, and one in a place where lessons nodloop approved reach yours. The judge sends the change, the anchor lines of its place with the text of the files you designate and of the rules files your sessions there loaded, and your own words on the runs it cites to the model of each member, which has 60 s to answer, and while curate runs in shadow its conforming decision only waits for a shadow question. Each decision is a `decide` trace with its tier, rule, the judge's classify trace, outcome, share and bin and the audit draw on its own id, and each cycle starts with a `knob` trace holding the knobs, the seed and the few-shot sets of the judge. A decision cut off before its write is carried out by the next pass. `curate.json` keeps the time of the last daily pass, the cycle, the knobs and the questions due for the hooks. `--daily` runs once a day and first drafts each corrected run of any producer that no extraction read, a correction younger than an hour left to its own stop, with one more try of an extraction whose model call failed. `--model` names the judge model only when a pass starts a judge configuration, which runs `claude-sonnet-5-5` at effort `high` otherwise, or the model of a chat endpoint
- `nodloop llm set chat --base-url <u> --model <m> [--key-env <ENV>]` points every command that calls a model, such as `knowledge extract`, `knowledge compact` and `llm probe`, at an OpenAI compatible Chat Completions endpoint like Ollama, vLLM, OpenAI, Gemini or a LiteLLM proxy, so background drafts need no claude login. `llm set claude` and `llm unset` go back to `claude -p`. The key is read from the env named and never saved. Every answer is checked against the schema and sent back once when it fails. A config.json that names chat without a model fails like one without a base URL. `nodloop config` lists the backend. The refusal a draft is resent with says the relation is add when the run reaches no item or candidate and lists the label keys the run carries, since a small local model kept the same mistake on the resend until it did
- Every extract trace of `knowledge extract` carries the usage of the drafter and critic calls summed, cost included, and the wall time of the extraction in `duration_ms`
- An extraction reads the waiting candidates the run reaches beside the approved items. A correction that repeats a candidate adds the run to its evidence and keeps its text, with conclusion `corroborated`, so it asks no new question. An update can name a candidate and a conflict names it too. The MCP `extraction` answer adds `candidates`, `propose_extraction` answers `corroborated`, and the extract trace adds `related` with the id, version and status it named
- When approving the candidate of `knowledge extract` would pass the 9000 chars of a run, the same process drafts a compaction of the fullest folder it reaches, checks its coverage and prints a `compaction` line. A pending compaction of that folder is reused and checked when it has no coverage yet
- `nodloop knowledge consolidate [--daily] [--model <m>]` asks the model which waiting candidates say the same lesson in other words, one call per cluster of candidates one run may carry together, and prints one line per group. It only records: a `consolidate` trace per producer with the groups, the candidates read, usage and duration, which `trace list --name consolidate` shows and retention keeps. No candidate is hidden, merged or approved. The stop hook starts `--daily` in a process of its own at most once a day, kept in `consolidate.json`, once two candidates wait
- `report critic` adds a row per member of the reaction point: answers asked and sure, and how they matched the verdict the conversation recorded on the same run as agree, disagree, missed correction, missed approval and deferred. A run whose verdict the reaction point recorded itself counts only as asked, and an answer of the capture never does since the capture records under reviewer `nodloop`. A member counts as sure from its answers to `corrects` and `approves` alone, so the questions the capture adds about lessons to stop following never move a row. A last `capture` line counts the runs the capture or the conversation judged: agree, disputed, capture only and conversation only, so you see how far the verdicts read from your words hold before a disputed run teaches nothing
- Every MCP tool lists an outputSchema, and every answer is checked against it before the client reads it. The answers keep their keys
- A session start after `/compact` or `/clear` adds every fitting item of the place again, since the context lost them, and records them as a `refill` trace so the next prompt adds none of them a second time, though `/clear` starts a new session id
- The new `hook subagent` SubagentStart hook adds every fitting item of the place to a subagent, since no prompt hook runs inside one. A session the holdout withholds gives its subagents no item either
- The nod skill approves, retires and reaffirms nothing on its own. It submits what you name through `intervene`, which decides once you confirm its form and otherwise is asked of you at the end of the turn, and on `/nodloop:nod` alone or a question such as what is waiting it shows what curate prepared and carried out since your last decision, read from the raw records. Its section on waiting drafts is gone
- `nodloop mcp --agent` serves the reviewer role: every tool but `approve`, `reaffirm` and `approve_compaction`, with every verdict and outcome recorded as the session's. `--agent --list` prints its tools
- Every decision and every proposal of the commands and tools that decide is an `intervention` trace naming the action `judge`, the version or compaction, the choice keep, undo or scope, the labels, its `authority`, its `proof` and the person it was recorded under, with the records it wrote, so `trace list --name intervention` shows who decided what
- `nodloop-server key add --person` marks a key a person holds
- Every named verdict carries `proof`: `key` under a nodloop-server key added with `--person`, `terminal` from `feedback add` at a terminal of your own, else `none`. A verdict of reviewer `session` or `nodloop` carries none
- Codex runs the plugin through `plugin/.codex-plugin/plugin.json`: the same launcher, skills and MCP server, and the hooks of `plugin/hooks/codex.json`, which are those of Claude Code with `--host codex`. Add it with `codex plugin marketplace add jeon-jihyeon/nodloop` and `codex plugin add nodloop@nodloop`, then trust its hooks in `/hooks`, since Codex skips plugin hooks until you do
- Cursor and Copilot CLI run the session start and the stop from the hook files in `examples/hooks`, copied into `.cursor/hooks.json` or `.github/hooks/`. The session start adds every fitting item, since neither host carries context on a prompt. Neither stop input holds the answer, so their stop records no run
- `nodloop hook <action> --host claude-code|codex|cursor|copilot` reads the input and writes the answer of that agent, and every run of a session carries a `host` label, `claude-code` when the flag is absent. An item scoped without `host` still reaches every host, and `--label host=codex` scopes one to Codex. A lesson drafted from a run leaves its `host` out of the scope unless the labels name it, so a lesson approved in Claude Code reaches the same place in Codex. A host refuses a hook it never runs
- `nodloop otel set --endpoint <url> [--protocol http/protobuf|http/json] [--headers-env <ENV>] [--no-logs] [--content]` saves an OTLP target in config.json once, and from then on every record reaches your tracing tool with no command: the stop hook starts `export otel --pending` in a process of its own after every recorded run, `nodloop mcp` after every run, verdict, outcome, approval, reaffirm and intervention, and `knowledge extract`, `knowledge consolidate`, `knowledge curate` and `session capture` after their traces. Claude Code removes every `OTEL_*` variable from hooks and MCP servers, so the standard variables alone start nothing. Headers are read from the variable `--headers-env` names at each export and never saved. `--no-logs` suits Langfuse, Phoenix and Datadog, which ingest no OTLP logs. `nodloop otel unset` stops it and `nodloop otel` prints it
- `export otel` sends OTLP protobuf by default, which Phoenix and Datadog need, or JSON with `--protocol http/json`, with no new dependency. Each record goes once as its own span with ids derived from the record, so an export again after a failure never counts anything twice: a trace per turn as an `invoke_agent <producer>` span from the prompt to the stop with the session as `session.id` and `gen_ai.conversation.id`, the items applied or withheld and the holdout arm, unit and share. Each verdict, outcome and approve or retire of a version is an `EVALUATOR` span named `nodloop.verdict`, `nodloop.outcome` or `nodloop.decision` and linked to what it judged, with the GenAI evaluation and the OpenInference annotation keys, plus a `gen_ai.evaluation.result` log record parented to that span. A decision links the question it answered or the judge that ran on it, else the extraction that drafted it. Every extraction, classify, coverage check, compaction draft, replay and consolidate is a trace of its own with an `invoke_agent nodloop.<name>` span and a `chat <model>` child carrying `gen_ai.usage.*` with cache read and write and `llm.cost.total`, linked to the run it judged and to the verdict that caused it. `--pending` keeps in `export.json` the position each store was read up to and sends once what was appended since, so a record a slower process appended late with an older time goes with the next export, and after one run at 20000 runs of 4 KB it takes 21 ms instead of the 467 ms of reading every store. A store whose record at the position a prune removed is read whole and sends what is stamped after the mark
- Outputs, reasons, notes, candidate text and the error of a failed run or model call go only with `--content` on `otel set` or `--with-content` on `export otel`, which still reads `--with-output`. Without it a failed span carries its error type and status alone, since an error may quote what a model wrote
- The prompt hook records the start of each turn as a `turn` trace with no text, and the stop hook stores how long the turn took as the run's `duration_ms`. A turn a stop hook continued counts from that stop. Retention removes `turn` traces past its cutoff
- `duration_ms` on the MCP tool `run`, `Run.Duration` in Go, `duration_ms` on `record` in Python and `durationMs` in TypeScript give a run its length, and every SDK adapter passes the time from its knowledge fetch to its record. A negative duration fails with `ErrDurationNegative`
- Model call traces name the model the backend answered with, such as `claude-haiku-4-5-20251001` for `haiku`: extract, replay, consolidate and a coverage check through a model. A coverage check records its usage and duration, a replay its duration, and every compaction draft through a model records a `compact` trace with its usage, duration and error, which retention keeps
- `model` on the MCP tool `run`, `Run.Model` in Go and `model` on `record` in both SDKs name the one model a producer runs. A session records none since a conversation may switch models
- The decision point `judge` asks whether your recorded decisions settle a change nodloop prepared and whether it goes against one of them. Every member answers and none is a fallback, since their disagreement is what turns a change into a question for you: three claude variants of one judge configuration, which differ in the order of the anchor lines and in a few-shot set of your earlier decisions drawn once when the configuration starts, plus an endpoint of another model family that `classifier set judge --url <u>` adds. Every variant runs at effort `high` passed to claude as `--effort`, since a default the host lowers, as Opus 5.5 did, would move the answers with nothing on record, and claude takes no temperature for variety. One classify trace keeps every member with the model it answered with, its effort and its answers, and the change, the anchor and your words only as an HMAC. The answers come out as conform, against, undecided or split with the share of conforming members and a confidence bin
- An endpoint in a classify trace names its model: the one it answered with, or else the one it was sent. An answer of NaN is refused like one past 1
- `schema/` publishes a JSON Schema 2020-12 file per record kind and version, every trace name, `verdict`, `outcome`, `knowledge` and `guard`, with `schema/kinds.json` listing each kind's version, store, link fields and free text fields. The input and output of each trace name are typed, and `nodloop schema [<kind>]` prints a file or lists the kinds. The files are generated from the Go types by `go generate ./cmd/nodloop` and a test fails when they drift. A field the index lists as text, such as the content of a knowledge record or the cwd of a guard entry, is never required, since a record page and the Data Package leave text out unless asked
- `hmac.key`, 32 random bytes of mode 0600 in the record directory, keys every hashed text. The first process creates it through a hard link of a synced temp file, so processes that start at once hash under one key. It never leaves the machine. On unix a key file another user may read or write fails every command and hook that loads it with an error naming its mode and `chmod 600`, and nodloop never repairs or replaces it
- The claude critic of `knowledge extract` names the model it answered with in a classify trace, and the trace names the model of the fallback member once it answered
- Eight trace names with published schemas, whose writers come with curate, the capture and the question path: `instructions`, `capture`, `decide`, `knob`, `anchor`, `expose`, `answer` and `rollup`. A `decide`, an `expose` and an `answer` carry the draw envelope `draw` with `cycle_id`, `policy_version`, `unit`, `seed`, `draw_id`, the probability `p` it was drawn with and `drawn`, and they and an `intervention` name their `source`: `push`, `manual` or `command`. A record you asked for carries no probability
- Knowledge records name `reason` on a retire, `decision` for the trace behind a status and `extract` for the extraction that proposed a candidate. A retire by a person records `person` and an approved compaction retires the items it merged with `compaction`. An import refuses a reason outside the set or on a record that is not retired
- Retention keeps the counts of each closed cycle of curate. Before a prune removes a run of a closed cycle it appends one `rollup` trace for it: per producer the undrawn runs, the shares drawn and per draw unit and arm the runs with their judged, corrected, same reason, named, inferred, audit and outcome counts, and per lesson and unit the runs that included it and those the item hold kept it from.
