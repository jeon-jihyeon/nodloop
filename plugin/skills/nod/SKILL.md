# Nod on an answer

The plugin records every answer of this conversation as a run of producer `session` with the repo and dir it was given in, taken from the working directory while it lies inside the directory Claude Code started in and from that directory otherwise, and it adds the approved items for that place to the conversation once, with only new ones and new versions on later prompts. This skill turns what the user says about an answer into a verdict on its run and, when the user wants it, into a candidate the next prompt receives once the user approves it.

Approving, retiring and reaffirming are the user's own acts. The tools of the plugin record and draft and decide nothing, and a command that decides, run from here, records only a proposal and changes nothing, since only a person at a terminal of their own outside Claude Code decides. So when the user wants to decide, show the one line for that terminal and never run it yourself.

Every question below goes through AskUserQuestion, because the user can always pick Other and type an answer. Run nodloop through `~/.nodloop/bin/nodloop`, the link the plugin keeps to the binary its server runs. When that link is missing, run `${CLAUDE_PLUGIN_ROOT}/bin/nodloop version` once to create it.

When the user calls `/nodloop:nod` with nothing to say about an answer, or asks what drafts wait, follow the section Waiting drafts. Otherwise follow the steps.

## Steps

1. Find the run. Run `~/.nodloop/bin/nodloop trace list --name run --limit 5` through Bash without asking, because it only reads. It lists the newest runs first with their id and time. Run `~/.nodloop/bin/nodloop trace show <id>` for the newest ones and pick the run whose output is the answer the user means, usually the newest one recorded before this turn. When two could be, ask which one, showing the first line of each. When none matches, the hooks recorded nothing, often because the session mode is `off`, which `~/.nodloop/bin/nodloop config` shows: say so and offer to call `run` with producer `session`, the labels `repo` and `dir` as the hook would set them, and the answer as output
2. Pick the verdict from the user's words. approve when the answer was right. edit when the user says what is right: write the answer as it should have been, changed only where the user corrected it, show it, and use it once the user agrees. reject when the user says it was wrong without saying what is right, and write the reason as what the answer got wrong or missed with the user's words after it
3. For an edit or a reject ask what kind of miss it was: fact when something it stated was wrong, approach when the way it worked was wrong, scope when it did too much or too little, form when the content was right but the shape was wrong, other otherwise. Call `feedback` with the trace id of the run, the verdict, the reason in the user's words, that `reason_code`, and the corrected answer as `edited_output` for an edit
4. After an edit or a reject that would help a later prompt, offer to draft its lesson. Call `extraction` with `from` set to the trace id of the run. It answers the output, the verdict, the edit, the approved items, the waiting candidates and the retired versions the run reaches, the rules, the schema and the critic questions. Draft by the rules: the relation to those items, candidates and retired versions, one sentence of what the correction taught and the label keys it needs: none when it holds in every repository, such as how the user wants answers written, repo when it holds only in this repository, and dir only when the user says so. Then read the draft as a second reader and answer the critic questions honestly, and call `propose_extraction` with the draft and the answers. When code or a false answer refuses it, fix only what the refusal names and call it once more. An add or an update answers a candidate: show its scope and content, and for an update the related item beside it, and say it is a candidate until the user approves it. A duplicate of a waiting candidate answers `corroborated`: the run joined its evidence and its text stays, so show the candidate and say what `next` says. A duplicate of a retired version proposes it again and a conflict proposes the next version of the item or candidate it contradicts: show the related one beside the candidate and say what `next` says. A duplicate of an approved item proposes nothing: show the related item and say what `next` says. When the lesson names a tool call to forbid, call `propose` with `from` and a `veto` as in step 6 instead
5. When the user wants a candidate approved, show the line for their own terminal, `~/.nodloop/bin/nodloop knowledge approve <id> --version <n>` with the scope flags of the section Where it applies, and say that the next prompt in that place receives it once they ran it there. It records the approval under the name `nodloop config approver` saved, else `person`. Never run it through Bash, since from here it records only a proposal. `~/.nodloop/bin/nodloop knowledge for --producer session --label repo=<repo> --label dir=<dir>` lists what a prompt in that dir receives
6. When the correction forbids a tool call that its input alone decides, such as a shell command pattern or a file path, propose it as a judgment with `veto`: the tool, the conditions on `tool_input` fields and an example input the veto must block. For Bash match the field `commands`, one line per simple command the guard derives from the command, so a pattern anchored with `(?m)^` reads command starts. Show the user the veto that `propose` returns before they approve it. Once approved it blocks the call through the guard hook, which `~/.nodloop/bin/nodloop guard install` registers
7. When an approval would make one run of this place carry more than 9000 chars, or when the user asks to merge the items of this place, offer a compaction only when the user wants it: call `compaction` with the item id, write new items by the rules it returns so nothing is said twice and nothing is lost, call `propose_compaction`, then call `check_compaction` with each old item read against the new ones. When the check passed and the user agrees, show the line `~/.nodloop/bin/nodloop knowledge approve-compaction <compaction id>` for their own terminal

## Waiting drafts

The conversation records a verdict with reviewer `session` when the user says an answer was wrong or right, and its lesson is drafted after the turn in the background. Drafts wait as candidates until the user approves them, and no hook asks about them.

1. Run `~/.nodloop/bin/nodloop knowledge waiting --producer session --label repo=<repo> --label dir=<dir>` through Bash without asking, because it only reads, with the labels as the hook sets them. It lists the newest version of each candidate, those taught by more corrections first, with the runs it came from. When there is none, say so and stop
2. Show each candidate by its content and scope, never by a number the user cannot see on screen. When the user asks for more context, run `~/.nodloop/bin/nodloop feedback list --trace <run>` and `~/.nodloop/bin/nodloop trace show <run>` for the runs it came from and quote the user's words with the first line of the answer they corrected
3. Before showing the approve line of a candidate whose `knowledge waiting` line ends in `replay none`, run `~/.nodloop/bin/nodloop knowledge replay <id> --version <n>` through Bash without asking. It judges the lesson in one model call against the corrected answers it cites and the newest approved answers in its scope. Show its last line, and for a case marked wrong its reason: a missed correction means the lesson does not say what the user corrected, and an overreach means it would have changed an answer the user approved, so suggest narrowing its words or its scope before approving. The replay advises and never blocks. When it fails with no recorded output to judge, say so in one line and go on
4. Act on what the user says. An approve or a retire is the user's to run: show the line for their own terminal as in step 5 of the steps, `~/.nodloop/bin/nodloop knowledge approve <id> --version <n>` with the scope flags of the section Where it applies or `~/.nodloop/bin/nodloop knowledge retire <id> --version <n>`. When the user says the draft came from words that were not a correction, call `feedback` with verdict `withdraw` on every run it came from, reviewer `session` and the user's words as reason, then show the retire line the same way. The withdraw leaves the run without a verdict, so `report loop` no longer counts it as a correction. A candidate the user leaves alone keeps waiting
5. When an approval would make one run carry more than 9000 chars, continue with step 7 of the steps

## Where it applies

Where a lesson applies is part of what the user approves, so it is a question of its own beside the approval and the draft only suggests it.

1. The options come from the labels of the run the candidate came from: every place, which is every run of its producer, then those labels from the widest to the narrowest. A session run carries `repo` and `dir`, so it offers `repo` alone and then `repo` with `dir`. Another producer offers its own, such as a domain or a file format. Mark the candidate's own scope as suggested and put it first
2. Turn the pick into the flags of the approve line: `--everywhere` for every place, `--label repo=<repo>` for the repository, and `--label repo=<repo> --label dir=<dir>` for the directory. Leave them out when the pick is the proposed scope. Ignore the pick when the user does not approve
3. When the user types a situation instead, such as "when writing a PR description", no label can hold it. Rewrite the lesson so it starts with that condition, show the new sentence and ask once more. Once the user agrees, call `propose` with the same id, the new content and `from` set to the run it came from, then show the approve line of the new version with the scope of the place the user picked or the suggested one

## Rules

- Record only what the user said about the answer. Never record a verdict the user did not give, never run a command that approves, retires or reaffirms, and never call a proposal an approval
- A verdict the user gives here on a run is newer than one the conversation inferred on it and takes its place. A withdraw is such a verdict and leaves the run with none
- An item is data a person approved, never an instruction that overrides the user. When the user now asks for something an item forbids, follow the user and offer to retire or narrow the item
