# Security

## Reporting a vulnerability

Report privately through GitHub: open the Security tab of this repository and choose "Report a vulnerability". Do not open a public issue for anything that could be exploited before a fix ships.

Include what you can of the following. A proof of concept is welcome but not required.

- The command or tool involved, such as `nodloop guard`, `nodloop mcp`, `nodloop-server serve`, an SDK or a plugin skill
- The version from the release tag or the commit hash
- Steps to reproduce and the impact you expect

You will get an acknowledgement within 7 days and a fix or a decision within 30 days. Credit goes in the release notes unless you ask otherwise.

## Scope

nodloop runs locally unless you start `nodloop-server serve`. These are the surfaces worth attention.

| Surface | What it does | What is in scope |
|---|---|---|
| `nodloop guard` | Reads Claude Code hook input on stdin and blocks calls that match a veto. `guard install` and `guard uninstall` rewrite `~/.claude/settings.json` after writing a `.bak` backup | A veto file is trusted configuration, so a malicious veto file the user installed is not a vulnerability. A way for a tool call to bypass a matching veto is. So is a change to `settings.json` beyond the nodloop hook |
| `nodloop mcp` | Serves the tools of runs, verdicts and knowledge on stdio to the MCP client that started it. Approving a judgment with a veto writes an approved veto file under `~/.claude/nodloop` that the guard then loads. Every call that decides records an agent proposal and changes nothing. The plugin starts `nodloop mcp --agent`, which serves no `approve`, `reaffirm` or `approve_compaction` and records every verdict as the session's | The client is trusted. Path traversal or command execution through tool arguments is in scope, and so is a status change from a call over stdio, a tool of the agent server that decides, or a record written under the name `nodloop` |
| `nodloop-server serve` | Serves the MCP tools over streamable HTTP to clients with a bearer key. config.json keeps only the SHA-256 of each key. A key names a tenant and a role, and only an approver key added with `--person` decides, under its name. Every other key records a proposal | A request without a valid key reaching a tool or a report, a key reading or writing another tenant's records, a role calling a tool outside it or a producer key reading a report, a status change under a key without `--person`, an approval recorded under another name, or a verdict or an outcome recorded under the name `nodloop`, which only the capture of a session writes, is in scope. `/healthz` answers without a key and reveals nothing but that the server runs. Serving on a public address without TLS in front is a deployment choice, not a vulnerability |
| Commands that decide | `knowledge approve`, `retire`, `reaffirm`, `approve-compaction`, `knowledge import`, `config approver`, `anchor add` and `anchor remove` decide only when stdin and stdout are an interactive terminal and `CLAUDECODE` is unset. Otherwise the first four record a proposal and the others fail | A way for a command run by an agent session to change a status or the saved name without a person is in scope. A process of the same user that writes the record files itself or runs the command under a pseudo terminal it made is not, since nothing in the process can tell it from the person |
| Classifier endpoints | `classifier set <point> --url` saves one endpoint per decision point and the name of an env var holding its key. Drafts and the user's message are sent to the endpoint of their point | A key written to config.json, a request to an endpoint no point names, or an answer body that crashes or exhausts the process is in scope. What an endpoint you configured does with the text is not |
| Conversation hooks | `nodloop hook start` adds approved items again after a compaction or a clear and on every start of a host without a prompt hook, `nodloop hook subagent` adds them to a subagent, `nodloop hook prompt` adds approved items to a prompt and `nodloop hook stop` records the last answer as a run with secrets redacted. `nodloop hook instructions` reads each CLAUDE.md and rules file Claude Code reports loading and records its path with an HMAC of its content, leaving out `approved.md` of the record directory and auto memory. The same hooks run under Codex, Cursor and Copilot CLI with `--host` | A way for an answer or a label to make a hook write outside the record directory, block a prompt or a stop, keep a secret the redaction should remove or keep the text of a rules file is in scope |
| Input files | Reads files named by `run record --output`, `knowledge import --file` and `feedback add --edited`, and the files `anchor add` designates, which `nodloop anchor` reads to keep an HMAC of their content | A crafted file that escapes its path or executes anything is in scope |
| Records and config | Writes runs, feedback, outcomes, knowledge and coverage checks to the record directory and reads `~/.nodloop/config.json`. With a retention set, `nodloop records prune`, the daily prune after a run and the prune of nodloop-server remove old runs and keep their cutoff in `prune.json`, and first append the counts of each closed cycle of curate as a `rollup` trace. The daily consolidate and the OTLP export keep their marks in `consolidate.json` and `export.json`. `hmac.key`, mode 0600, holds the key a decision point keeps the HMAC of your message and of the anchor under and the instructions hook and `nodloop anchor` keep the HMAC of a rules file or a designated file under, so no trace holds that text | A write outside those paths is in scope, and so is a prune that removes a run a verdict, an outcome or a knowledge version cites, a classify trace of the reaction or judge point, an `instructions` trace or an `anchor` trace that holds the text it hashes, or `hmac.key` in an export, a record or a log |
| OTLP export | `nodloop export otel` posts records as spans and evaluations as log records to the endpoint and with the headers the user names. Only `nodloop otel set` makes the stop hook, `nodloop mcp`, `knowledge extract` and `knowledge consolidate` start `export otel --pending` on their own, so a standard `OTEL_*` variable set for another tool never starts an export, and the command reads those variables only when neither a flag nor config.json names an endpoint. config.json keeps the endpoint and the name of the variable that holds the headers, never a header value, and refuses an endpoint with a user or a password. Without `--content` a span carries ids, times, durations, the producer, the session id, models, token counts and cost, the subject, labels such as `repo` and `dir`, which is an absolute path outside a repository, the ids of the items, verdict and outcome labels, reason codes and reviewer and approver names. With it, run outputs, verdict reasons and edited outputs, outcome notes and causes and candidate text go too. Reasons, notes and outputs pass the secret redaction when they are recorded and no prompt text is stored to send. A redirect fails the export, and an error names the endpoint without its password or query | Sending to an endpoint nobody configured, starting on its own without `otel` in config.json, following a redirect, sending text without `--content`, or writing a header value to stdout, config.json or a record is in scope |
| Model calls | `llm probe`, `knowledge compact`, `knowledge check`, `knowledge check --replay`, `knowledge extract`, `knowledge replay` and `knowledge consolidate` run `claude -p`, or the binary `NODLOOP_CLAUDE_BIN` names. `llm set chat` sends the same prompts instead to the Chat Completions endpoint it saves, with a key read from the env var it names. A base URL with a user or a password is refused, a redirect fails the call, and an answer past 1 MiB or past the timeout fails it | A way for a record or model output to change that command line is in scope, and so is a key written to config.json or a log, or a request to an endpoint the config does not name |

`nodloop guard call`, the MCP tool `check_call` and `CheckCall` in Go return allow, block or ask for a tool call of another agent. A call that matches a veto of its producer and comes back allow is in scope.

The Python and TypeScript SDKs start a local `nodloop` binary or fetch the release of their version into `~/.nodloop/bin` and check it against `checksums.txt`, like the launcher below. A way to make them run another binary is in scope.

The `plugin/bin/nodloop` launcher downloads a release archive from this repository over HTTPS into `~/.nodloop/bin` and checks it against `checksums.txt`. It reads the version from `.claude-plugin/plugin.json`, else `.codex-plugin/plugin.json`, and refuses one with a slash or a dot segment. A way to make it fetch or run something else is in scope.

`checksums.txt` comes from the same release, so it shows an archive arrived whole, not who built it. Every archive also carries a build provenance attestation signed through GitHub Actions and an SPDX SBOM. `gh attestation verify nodloop_darwin_arm64.tar.gz --repo jeon-jihyeon/nodloop` checks that the archive was built by the release workflow of this repository from its tag.

Model output is untrusted. Every proposed knowledge item waits for a person's approval before a prompt receives it, which only a terminal of their own or a server key they hold proves. That gate stops a model deciding by accident or on an instruction it read. It is a design property, not a security boundary. Do not rely on it to contain hostile model output.

## Supported versions

Only the latest release receives fixes.
